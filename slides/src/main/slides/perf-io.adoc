=== I/O bound

* the CPU is idle, threads *wait* for a disk, a socket or another service
* faster code does not help, *fewer and cheaper* waits do
* and the hidden part: (de)serialization, the CPU and allocation price of every I/O

=== Fewer round trips

[mermaid,format=svg]

* *N+1*: one query for a list, then one more query for each element (typical ORM trap)
* *batching*: many operations in one request (`IN (...)`, JDBC batch, bulk APIs)
* *pipelining*: send the next request before the previous response arrived (Redis, HTTP/2)
* *caching*: serve repeated reads from memory, accept staleness

=== Buffering and the cheap I/O techniques

* small writes into a buffer, one big system call (`BufferedOutputStream`, 8 KB default)
* `readv` / `writev` for header + body in one call
* `transferTo` for file to socket or file to file: data never enters the heap
* the details and pictures: Java I/O chapter, ways to do I/O

=== Technique: when to use it

[cols="2,3",options="header"]
|===
|Technique |Use it when
|buffered streams |many small reads/writes
|vectored I/O |several pieces (header, body) go together
|memory mapped file |random access to a big file, read mostly
|`transferTo` (zero copy) |serving files, copying, no need to look at the data
|direct I/O |you run your own cache (database-like)
|`force()` / `fsync` |only where durability is required, it is the slow part
|===

=== Virtual threads and I/O: what to know

* final in Java 21 (JEP 444), details in the virtual threads chapter
* socket I/O is non-blocking underneath, the virtual thread unmounts while waiting
* *file I/O still blocks the carrier thread*, the scheduler may temporarily add carriers to compensate
* Java 24 (JEP 491): `synchronized` no longer pins the carrier, remaining pinning: native frames, class initialization
* virtual threads help *waiting*, not CPU: they remove the thread limit, so limit the downstream with a semaphore or pool

=== Timeouts and retries

[mermaid,format=svg]
----
sequenceDiagram
  participant A as client
  participant S as server
  A->>S: try 1
  Note over A: timeout
  A->>S: try 2 after 100 ms + jitter
  Note over A: timeout
  A->>S: try 3 after 200 ms + jitter
  S-->>A: response
----

* every remote call needs a timeout (connect and read), the default is often *infinite*
* retry only idempotent calls, with a limit and exponential back-off
* *jitter* (random delay): clients do not retry in lockstep and flatten the server again
* retries multiply load: a retry storm kills a recovering service

=== Serialization and deserialization

* *serialization*: object graph to bytes, *deserialization*: bytes back to objects
* every request crosses it twice: client and server
* CPU heavy (reflection, parsing, conversions) and allocation heavy (Strings, byte arrays, objects)
* often the hidden part of "I/O time": profile before blaming the network

=== Formats: overview

[cols="2,2,3",options="header"]
|===
|Format |Kind |Remark
|JSON (Jackson) |text, schema-less |readable, universal, slowest and biggest
|Protocol Buffers |binary, schema-first |compact, generated code, good evolution
|Avro |binary, schema-first |schema travels or is in a registry, big data
|MessagePack / CBOR |binary, schema-less |JSON data model, smaller and faster
|FlatBuffers, Cap'n Proto, SBE |binary, zero-copy |no decode step, fixed layout
|Java serialization |binary, built in |avoid
|===

=== Java built-in serialization: avoid

* slow and large: reflection, class descriptors and metadata in the stream
* fragile: tied to class structure and `serialVersionUID`
* *security*: deserialization can instantiate attacker chosen classes, a long history of remote code execution bugs
* if you must keep it: serialization filters (JEP 290, context-specific filters JEP 415) with an allow list
* for new code use a format with a schema; records are a good fit as the data carriers

=== Streaming parser example

[source,java]
----
try (JsonParser p = factory.createParser(in)) {      // Jackson streaming API
  while (p.nextToken() != null) {
    if (p.currentToken() == JsonToken.FIELD_NAME
        && p.currentName().equals("id")) {
      p.nextToken();
      long id = p.getLongValue();                    // no intermediate objects
    }
  }
}
----

* skips what you do not need, no tree, no POJOs
* the same idea for writing: `JsonGenerator` straight into the output stream

=== Avoid reflection

* classic data binding discovers fields by reflection at runtime: slow start, hard for native image and AOT
* faster: code generation at build time (protobuf, Avro, annotation processors, Jackson afterburner-style bytecode generation)
* records: a compact, final shape, easy to bind (supported by common libraries)
* Java 25 AOT cache (Leyden) helps startup, it does not remove the per-message work
* warm up: first requests run in the interpreter, see the JIT chapter

=== Buffer reuse and fewer copies

[source,java]
----
// copies: bytes -> String -> parse -> object
String s = new String(bytes, UTF_8);
Order o = mapper.readValue(s, Order.class);

// better: parse straight from the stream or array
Order o = mapper.readValue(in, Order.class);
----

* avoid the intermediate `String` and `byte[]` copies, hand the parser the stream
* reuse buffers (thread-local or pooled), mind that pooled buffers need care with virtual threads
* write with a reused `ByteArrayOutputStream` / `ByteBuffer` instead of new ones per message
* fewer allocations = fewer young collections, see the GC chapter

=== Parsing from ByteBuffer and MemorySegment

[source,java]
----
MemorySegment seg = channel.map(MapMode.READ_ONLY, 0, size, arena);

int  id    = seg.get(ValueLayout.JAVA_INT_UNALIGNED, 0);
long price = seg.get(ValueLayout.JAVA_LONG_UNALIGNED, 4);
----

* FFM API is final since Java 22 (JEP 454): `long` offsets, deterministic release via `Arena`
* read fixed layouts directly from mapped files or off-heap buffers, no `byte[]` copy, no objects
* a natural fit for zero-copy formats; `ByteBuffer` does the same with `int` offsets
* bounds are checked, you pay safety with a little CPU

=== Lazy deserialization

* *lazy*: keep the bytes, decode a field or nested message only when somebody asks
* good for proxies, routers, filters that look at a header and forward the rest untouched
* zero-copy formats are lazy by design
* risk: the buffer must stay alive, errors in data appear late, repeated access decodes repeatedly

=== Schema evolution

* *schema evolution*: old and new versions of the schema must read each other's data (rolling deploys, stored data)
* protobuf: add optional fields with new numbers, never reuse numbers
* Avro: reader and writer schemas are resolved, defaults make fields optional
* JSON: tolerant by convention (ignore unknown fields), but nothing enforces it
* zero-copy formats: only append fields, layouts are rigid
* flexibility costs bytes or CPU; decide how often you change versus how hot the path is

=== I/O bound: summary

* recognise: low CPU, waiting threads, slow device or dependency
* investigate: JFR socket/file events, thread dumps, `iostat`, `ss`, tracing
* first do less I/O (batching, N+1, caching), then make it cheaper, then wait smarter
* protect yourself: timeouts, jittered retries, back-pressure, bounded pools
* do not forget serialization: choose the format for the boundary, avoid copies and reflection
