=== No magic

[mermaid,format=svg]
----
flowchart LR
  c["code"] --> b["benchmark"] --> p["profile"] --> r["repeat"]
  r --> c
----

* there is no magic spell, no secret ingredient
* claims that "X is fast / slow" without benchmark code and numbers are useless
* make it correct, make it clear, make it concise, *make it fast, in that order* (Wes Dyer)
* observability (see the <<voyeurs_in_the_jvm_land,observability chapter>>) tells you *where* to look, benchmarks tell you if a change *helped*

=== Macro and micro

[cols="1,2,2",options="header"]
|===
| |Micro benchmark |Macro benchmark
|measures |one method or a small component |the whole system under realistic load
|tool |JMH |load generators: JMeter, Gatling, k6, wrk2
|good for |comparing implementations, regressions in a hot path |capacity, latency percentiles, SLOs
|risk |measures something that doesn't matter |noisy, slow to run, hard to explain
|===

=== The naive benchmark

[source,java]
----
long start = System.currentTimeMillis();
for (int i = 0; i < 100_000; i++) {
  // do stuff
}
long stop = System.currentTimeMillis();
----

it prints a number, but is the number *right*?

=== Why the naive benchmark lies

[mermaid,format=svg]
----
flowchart LR
  t0["start:<br/>interpreter"]:::r --> t1["hot loop:<br/>C1 compiles"]:::y --> t2["hotter:<br/>C2 compiles"]:::g --> t3["steady state"]:::g
  classDef r fill:#ef9a9a,stroke:#c62828,color:#000
  classDef y fill:#fff59d,stroke:#f9a825,color:#000
  classDef g fill:#a5d6a7,stroke:#2e7d32,color:#000
----

* *warm-up*: the first iterations run in the interpreter, then in C1 code, the number you get is an average of all of them
* *dead code*: the loop body has no visible effect, the JIT may delete it, you measure an empty loop
* *constant folding*: constant inputs let the JIT compute the result at compile time
* timer resolution, GC pauses and a busy machine add *noise*
* the loop might even be compiled by OSR in the middle (see the <<jit_me_baby_one_more_time,JIT chapter>>)

=== What a good harness must do

[mermaid,format=svg]
----
flowchart LR
  f["fork a fresh JVM"] --> w["warm-up iterations<br/>(not measured)"] --> m["measurement iterations<br/>(measured)"] --> s["statistics"]
  m --> bh["consume the result<br/>(no dead code)"]
----

* isolate every benchmark in its *own JVM* (a fork), so profiles don't leak between them
* run until the JIT reaches steady state, *then* measure
* make sure results are *used*, inputs are *not constants*
* report averages *with error*, not a single run

=== JMH

[quote,JMH,]
a Java harness for building, running, and analysing nano/micro/milli/macro benchmarks written in Java and other languages targeting the JVM

* by the OpenJDK team (the people who write the JIT), https://openjdk.org/projects/code-tools/jmh/[openjdk.org/projects/code-tools/jmh]
* current release 1.37, works with JDK 25
* benchmarks are Java classes with annotations, JMH generates the code that runs them
