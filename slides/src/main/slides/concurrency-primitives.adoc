=== Atomicity: is `i++` safe?

[source,java]
----
int i = 0;
i++;
----

[source,bytecode]
----
iload_1
iconst_1
iadd
istore_1
----

* four bytecodes, and even a single `inc [mem]` instruction is load + add + store μops
* another core can write in between: a lost update
* needs a *read-modify-write* that is atomic in hardware

* one instruction, atomic across all cores: the core owns the cache line for its duration (`lock` prefix)
* other atomics: `lock xadd` (fetch-and-add), `xchg`
* ARM: load-linked / store-conditional (`ldxr`/`stxr`) or `cas` instructions (LSE)

=== java.util.concurrent.atomic

[source,java]
----
// AtomicInteger.incrementAndGet(), conceptually
int prev;
do {
  prev = get();
} while (!compareAndSet(prev, prev + 1));
----

* `AtomicInteger`, `AtomicLong`, `AtomicReference` call *intrinsics*, JIT turns them into `lock cmpxchg` / `lock xadd`
* under high contention CAS keeps failing and the cache line ping-pongs
* `LongAdder`: spreads updates over several cells (padded with `@Contended`), sums on read

=== synchronized

* `monitorenter` / `monitorexit` bytecodes, javac adds a `try/finally` so the monitor is always released
* the lock state lives in the object header (*mark word*)
* reentrant, no fairness, released automatically at the end of the block
* since Java 24 a virtual thread blocked on `synchronized` no longer pins its carrier thread (JEP 491)

=== Monitor states

[mermaid,format=svg]
----
stateDiagram-v2
  direction LR
  free: unlocked
  thin: lightweight lock<br/>CAS on header / lock stack
  fat: inflated<br/>ObjectMonitor
  [*] --> free
  free --> thin: lock (CAS)
  thin --> free: unlock
  thin --> fat: contention, wait(),<br/>hashCode
  fat --> free: deflated when idle
----

* uncontended: one CAS, no OS involvement
* contended: *inflate* to a heavyweight monitor, spin briefly, then the thread *parks* (OS call)
* biased locking (a third state) was disabled in 15 and removed in 18

=== java.util.concurrent.locks

[cols="1,2",options="header"]
|===
|`synchronized` |`ReentrantLock`
|block scoped, automatic unlock |explicit `lock()` / `unlock()` in `finally`
|no timeout, not interruptible |`tryLock(timeout)`, `lockInterruptibly()`
|one wait set (`wait`/`notify`) |many `Condition`s
|unfair |fair or unfair
|JVM implementation |plain Java on top of `AbstractQueuedSynchronizer`
|===

* also `ReentrantReadWriteLock`, `StampedLock` (optimistic reads, not reentrant)

=== Concurrent collections

[cols="2,3",options="header"]
|===
|Class |Technique
|`ConcurrentHashMap` |CAS to insert into empty bins, `synchronized` on the head of a bin otherwise, lock-free reads
|`CopyOnWriteArrayList` |every write copies the array, reads need no locks
|`ArrayBlockingQueue` |one lock, bounded ring buffer
|`LinkedBlockingQueue` |two locks (head and tail)
|`ConcurrentLinkedQueue` |lock-free (Michael-Scott), CAS on head and tail
|===

=== Thread pools

* `ExecutorService` = a queue of tasks + a set of worker threads
* `ForkJoinPool`: one deque per worker, idle workers *steal* from the others
* platform threads are 1:1 with OS threads, so they are expensive: see the <<virtual_threads,virtual threads chapter>>
* `ThreadLocal` costs memory per thread, `ScopedValue` (final in Java 25, JEP 506) is the immutable, bounded alternative
