=== Reordering

[source,java]
----
class Reordering {
  int x = 0, y = 0;

  void writer() {     // thread 1
    x = 1;
    y = 2;
  }

  void reader() {     // thread 2
    int r1 = y;
    int r2 = x;
  }
}
----

=== Reordering: possible results

[cols="1,1,3",options="header"]
|===
|r1 |r2 |Explanation
|0 |0 |reader ran before the writer
|2 |1 |reader ran after the writer
|0 |1 |reader saw `x = 1` but not yet `y = 2`
|*2* |*0* |writes reordered (compiler, store buffer, cache), reader saw `y` but not `x`
|===

=== Who reorders?

[ditaa]
----
Java source ---> javac ---> bytecode ---> JIT compiler ---> CPU ---> caches
                                              |               |         |
                                      reorders, caches   out-of-order,  delayed
                                      values in registers  store buffer  visibility
----

* the JIT may move, merge or remove memory accesses, as long as *one thread* cannot tell
* the CPU may execute and publish them in another order
* result: no global order of all memory operations unless the program asks for one

=== Visibility

[source,java]
----
boolean stop = false;            // not volatile

void worker() { while (!stop) { /* work */ } }   // thread 1
void main()   { stop = true; }                   // thread 2
----

* the JIT may hoist the read of `stop` out of the loop: `if (!stop) while (true) { ... }`
* the worker may never stop, a legal outcome
* declaring `stop` `volatile` forbids this optimization

=== The Java Memory Model (JSR-133, Java 5)

* a *specification* of which values a read of a shared variable may return
* defines a partial order called *happens-before*
* if write W *happens-before* read R, R sees W (or a later write)
* if two accesses to a variable are not ordered by happens-before and one is a write, it is a *data race*
* *promise*: a program without data races behaves as if it were sequentially consistent

=== Happens-before rules

[graphviz]
----
digraph {
	rankdir=LR
	node [shape=box]
	subgraph cluster_t1 { label="Thread A"; w [label="write x"]; u [label="unlock m /\nwrite volatile v /\nThread.start()"] ; w->u [label="program order"] }
	subgraph cluster_t2 { label="Thread B"; l [label="lock m /\nread volatile v /\nstarted thread runs"]; r [label="read x"]; l->r [label="program order"] }
	u->l [label="happens-before", color=red, fontcolor=red]
}
----

* program order inside a thread
* monitor *unlock* -> later *lock* of the same monitor
* *volatile write* -> later *volatile read* of the same variable
* `Thread.start()` -> first action of the thread, last action -> `join()` returns
* end of constructor -> *final fields* visible to anyone who gets the reference safely

=== volatile

[source,java]
----
volatile boolean ready;
int data;

// thread 1                // thread 2
data = 42;                 if (ready) {
ready = true;                 use(data);     // always sees 42
                           }
----

* every read sees the latest write (*visibility*)
* writes before a volatile write are visible after the matching volatile read (*ordering*)
* *not atomic* for compound actions: `count++` on a volatile is still a race

=== Memory barriers

[cols="1,3",options="header"]
|===
|Barrier |Guarantee
|LoadLoad |earlier loads complete before later loads
|LoadStore |earlier loads complete before later stores
|StoreStore |earlier stores are visible before later stores
|StoreLoad |earlier stores are visible before later loads (*most expensive*, drains the store buffer)
|===

* the JIT/interpreter emits the cheapest instruction sequence for each platform
* the same Java code yields different machine code on x86 and AArch64

=== volatile in machine code

[cols="1,2,2",options="header"]
|===
| |x86-64 |AArch64
|volatile read |plain `mov` |`ldar` (load-acquire)
|volatile write |`mov` + `lock addl $0,(%rsp)` (StoreLoad fence) |`stlr` (store-release)
|`synchronized` |`lock cmpxchg` on lock, release store on unlock |`ldaxr`/`stlxr` or `casal`
|===

* on x86 only StoreLoad needs an instruction, other reorderings never happen in hardware
* but the *JIT* must still not reorder them, barriers are also compiler barriers

=== VarHandle access modes

[cols="1,3",options="header"]
|===
|Mode |Guarantee
|plain |none, like a normal field access
|opaque |coherent per variable, not reordered with itself, no ordering with others
|acquire / release |one-way ordering, enough for most publish / consume patterns
|volatile |full ordering, sequentially consistent
|===

* `VarHandle` (Java 9) exposes what the JMM and CPU provide, `Unsafe` is on its way out
* `Thread.onSpinWait()` hints the CPU that we are in a spin loop

=== Safe publication and final fields

[source,java]
----
class Holder {
  final int value;
  Holder(int v) { value = v; }
}
static Holder shared;          // thread 1: shared = new Holder(42);
                               // thread 2: shared != null  =>  shared.value == 42 ?
----

* *final fields*: after the constructor, every thread that sees the reference also sees the field values (a *freeze* barrier)
* non-final fields can appear as `0` / `null` if the reference is published through a data race
* don't let `this` escape from a constructor
* safe ways: `volatile`, `synchronized`, `final`, concurrent collections, static initializer
