=== Collectors in OpenJDK 25

[cols="2,1,1,2,2",options="header"]
|===
|Collector |Generational |Compaction |Marking / moving objects |Pause

|Serial |yes |STW |STW, single thread |proportional to live set
|Parallel |yes |STW |STW, many threads |proportional to live set
|G1 |yes (regions) |STW evacuation |concurrent marking, STW evacuation |bounded by pause goal, ms - 100s ms
|Shenandoah |yes (since 25) |concurrent |concurrent marking and evacuation |ms, independent of heap size
|ZGC |yes (only mode since 24) |concurrent |concurrent marking and relocation |sub-ms, independent of heap size
|Epsilon |no |none |no GC at all |none, JVM exits when heap is full
|===

=== What changed since Java 8

[cols="1,4",options="header"]
|===
|JDK |Change
|8 |Parallel is the default, CMS available
|9 |G1 becomes the default (JEP 248)
|10 |G1 full GC is parallel (JEP 307)
|14 |CMS removed (JEP 363)
|15 |ZGC and Shenandoah are product features (JEP 377, 379)
|21 / 23 |Generational ZGC added / made default (JEP 439, 474)
|24 |non-generational ZGC removed (JEP 490)
|25 |Generational Shenandoah (JEP 521), compact object headers (JEP 519)
|===

=== Default collector and selection

* also: G1 region pinning for JNI (22), G1 late barrier expansion (24), compact object headers (25)
* *default collector*: G1, or Serial when the JVM sees < 2 CPUs or < 1792 MB memory
* select explicitly: `-XX:+UseSerialGC`, `-XX:+UseParallelGC`, `-XX:+UseG1GC`, `-XX:+UseZGC`, `-XX:+UseShenandoahGC`

* *Serial*: one thread, tiny footprint, good for small heaps and containers with 1 CPU
* *Parallel*: same algorithms with many threads, best raw throughput
* both pause the application for the whole young or old collection
* pause grows with live data (young) or heap size (old / full)

=== Why G1?

* Parallel / Serial: Old collection pause grows with heap size
* heap sizing of generations had to be done by hand
* G1 idea: split the heap into many small *regions* and collect only some of them per pause
* pause time is limited by *how many regions* we collect, not by heap size

=== G1: remembered sets

[mermaid,format=svg]
----
flowchart LR
  A["region A (old)"] -- "reference" --> B["region B"]
  B -.- R["RSet of B: card 17 of A points into me"]
----

* G1 can collect *any* subset of regions, so each region keeps a *remembered set* of incoming references from other regions
* post-write barrier puts the dirty card in a *queue*, *refinement threads* update the remembered sets concurrently
* during evacuation the RSet of each region in the collection set is a root

=== G1: concurrent marking cycle

[mermaid,format=svg]
----
flowchart LR
  y1["young GC"] --> cs["Concurrent Start<br/>(STW, in a young GC)"]:::stw
  cs --> cm["Concurrent Mark<br/>(app keeps running,<br/>young GCs continue)"]:::conc
  cm --> rm["Remark<br/>(STW)"]:::stw
  rm --> cl["Cleanup<br/>(frees empty regions)"]:::stw
  cl --> mx["mixed GCs<br/>(young + old regions)"]:::stw
  classDef stw fill:#ef9a9a,stroke:#c62828,color:#000
  classDef conc fill:#a5d6a7,stroke:#2e7d32,color:#000
----

* starts when heap occupancy crosses *IHOP* (initiating heap occupancy, adaptive, ~45% initially)
* *concurrent start* piggybacks on a young pause: scans roots
* concurrent mark computes *live bytes per region*, application keeps running
* *remark* (STW) finishes marking, *cleanup* frees fully empty regions

=== G1: SATB marking

* marking runs while the application changes the graph
* G1 marks the *snapshot at the beginning* (SATB): everything reachable at the start stays live
* pre-write barrier logs the *overwritten* reference so the collector still visits it
* objects allocated during marking are implicitly live
* result: *floating garbage* (died after the snapshot), freed in the next cycle

  class h1,h2,h3 H
  class f F
----

* object >= 50% of a region => allocated directly in *contiguous* old regions
* never copied in young collections, freed when dead (can be reclaimed eagerly)
* can fragment the heap, may force extra concurrent cycles

=== G1: when things go wrong

* *evacuation failure*: no free region to copy into, objects stay where they are, expensive pause
* *Full GC*: last resort, STW mark-compact of the entire heap (parallel)
* pinned regions (JNI critical sections) are skipped, they no longer block GC (since 22)
* the aim of concurrent cycle + mixed GCs is to never get here

* regionalised like G1, but objects are *moved while the application runs*
* the hard part: moving an object while threads read and write it

=== Shenandoah: load reference barrier

[mermaid,format=svg]
----
flowchart LR
  L["load reference"] --> Q{"in collection<br/>set?"}
  Q -- "no" --> U["use it"]:::conc
  Q -- "yes" --> F{"already<br/>forwarded?"}
  F -- "yes" --> R["return the new copy<br/>and fix the slot"]:::conc
  F -- "no" --> C["copy object<br/>CAS installs forwarding ptr"]:::stw --> R
  classDef stw fill:#ef9a9a,stroke:#c62828,color:#000
  classDef conc fill:#a5d6a7,stroke:#2e7d32,color:#000
----

* every reference *load* goes through a barrier, so mutators always see the one current copy
* forwarding pointer lives in the object's mark word (the extra Brooks pointer word was removed in JDK 13)
* plus SATB pre-write barrier for concurrent marking
* mutator and GC threads race to copy, only one CAS wins

=== Shenandoah: cycle

[cols="2,1,3",options="header"]
|===
|Phase |STW? |Work
|Init Mark |yes |scan roots (short)
|Concurrent Mark |no |trace object graph (SATB)
|Final Mark |yes |drain queues, choose collection set
|Concurrent Evacuation |no |copy live objects out of collection set
|Init Update Refs |yes |tiny, sync threads
|Concurrent Update Refs |no |fix all references to moved objects
|Final Update Refs |yes |fix roots, recycle regions
|===

* pauses depend on root set size, not on heap size

=== Shenandoah: generational mode

* *generational mode* (product in JDK 25, `-XX:ShenandoahGCMode=generational`): frequent young cycles, old cycles rarely

* the check is a bit test per loaded reference

* generational ZGC adds *store barriers* to track old->young references

* heap is a set of *pages*; garbage-heavy pages are evacuated into new pages
* *forwarding table* per page (off-heap): old address -> new address
* stale references are fixed lazily by the load barrier or the next marking

[mermaid,format=svg]
----
flowchart LR
  a["Pause<br/>Mark Start<br/>STW"]:::stw --> b["Concurrent<br/>Mark"]:::conc --> c["Pause<br/>Mark End<br/>STW"]:::stw --> d["Concurrent<br/>Relocate"]:::conc
  classDef stw fill:#ef9a9a,stroke:#c62828,color:#000

----

* three tiny pauses (roots), everything else concurrent, sub-millisecond typical
* *generational*: young and old collected independently, so short-lived garbage is cheap
* *allocation stall*: if the app allocates faster than ZGC reclaims, allocating threads wait

=== Epsilon

* "no-op" collector: allocates, never reclaims
* JVM exits with `OutOfMemoryError` when heap is full
* use for: benchmarks (zero GC noise), short-lived jobs, GC-free design experiments
* `-XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC`
